首次必做

E2 的 udev 规则

不装的话 rfp-cli 报 E3000201: Cannot find the specified tool——设备节点默认是 root:root 0664，普通用户只读。

cd <bao-benchmarks-portable> && ./install-udev-rule.sh   # 需要 sudo
# 装完把 E2 拔插一次

规则内容就一行：SUBSYSTEM=="usb", ATTR{idVendor}=="045b", ATTR{idProduct}=="82a1", MODE="0666"

02编译

export PATH=/usr/local/Renesas/CC-RH/V2.08.00/bin:$PATH
make PLATFORM=rh850-u2a-vm1+vm2 CONFIG=autosar-vm0+vm1

产出 bin/rh850-u2a-vm1+vm2/autosar-vm0+vm1/bao.bin，约 45.9 KB。

CC-RH V2.08.00 会拒绝几处 C99 写法（匿名 struct/union 上的 designated initializer， 错误码 E0523134），修复已在本分支提交，细节见 GCC 到 CC-RH 的移植分析。

guest 用 VM_IMAGE_LOADED 声明，不内嵌进 bao.bin，单独烧到各自地址。 这也顺带绕开了 CC-RH 不支持 .incbin 的问题。

脚本

./flash/flash.sh            # guest + bao，最后释放复位
./flash/flash.sh bao        # 只烧 bao（guest 已在 flash 里）
./flash/flash.sh guests     # 只烧两个 guest
./flash/flash.sh reset      # 只释放复位

脚本内部就是三条 rfp-cli，参数取自 bao-benchmarks-portable 里那份 runme-rh850-u2a16.sh：

echo ffff | rfp-cli -device "RH850/U2x" -tool e2 -osc 40.0 \
    -program -file flash/guests/vm0-autosar-0x10000.hex
echo ffff | rfp-cli -device "RH850/U2x" -tool e2 -osc 40.0 \
    -program -file flash/guests/vm1-mcal-0x7F0000.hex
echo ffff | rfp-cli -device "RH850/U2x" -tool e2 -osc 40.0 \
    -program -bin 0x0 bin/<platform>/<config>/bao.bin -run
  • ffff 是 ID code，从 stdin 喂给 rfp-cli
  • -osc 40.0 主时钟 40 MHz
  • guest 是 -program -file（hex 自带地址），bao 是 -program -bin 0x0
  • 不要用 -erase-chip，逐块编程即可，否则会把已烧的 guest 抹掉
  • -run 释放复位让板子跑起来

RFP_DIR 环境变量可覆盖 rfp-cli 位置，PLATFORM / CONFIG 可覆盖要烧哪个构建。

04串口

两个坑

波特率 500000，且不是 E2 的口

波特率写死在 src/platform/drivers/renesas_rlin3/renesas_rlin3.c 的 uart_init() 里（LPRS_16 | NSPB_10，假设 CLK_RLIN = 80 MHz）， 注释标的就是 500000。按 115200 抓什么都收不到。

串口是独立的 CH340（1a86:55d3）接在 RLIN35 上，节点恰好也叫 /dev/ttyACM0，容易误以为是 E2 的虚拟口。 

picocom -b 500000 /dev/ttyACM0

正常启动应该看到横幅，随后是持续的数据流，约 386 B/s：

MCAL guest 带一个交互 shell，回车会回显提示符。若出现 BAO ERROR: 通常是配置声明的内存区超出平台描述符给的范围。

05CAN 排查

串口先跑通了，CAN 却一直没信号。手上三个现成配置全都不行——排查花的时间比编译本身长得多。

对照实验（guest 全程相同）
Bao配置串口CAN
本次构建vm1+vm2.c只有横幅，命令表空无
本次构建twovm.c同上无
参考镜像失传386 B/s有
本次构建autosar-vm0+vm1.c
反解得到		386 B/s有

排查中还岔出过一条弯路：起初以为 guest 固件不配对。odyssey 仓库里那对 2025-04 的 guest 确实与参考镜像那对不是一代（355 KB vs 561 KB）， 换成 autoshow/bins-to-flash 那对后串口才正常。但 CAN 仍然没有—— 说明还有第二个问题。

根因

CAN VM 没有映射 INTC1

CAN 控制器是 RSCFD0 @ 0xFFF50000，依赖 8 个中断 {296, 297, 304, 305, 306, 319, 320, 321} 经中断控制器路由到 VM。

twovm.c 和 vm1+vm2.c 都没有给 VM0 映射 INTC1 （0xFFFC0000，16 KB），而反解出来的参考配置有。 中断进不去，CAN 控制器就只能静默——而串口 VM 的中断走另一条路径，不受影响。 症状就成了「日志一切正常，唯独 CAN 没有」。

06配置反解

参考镜像 bao_AutoSar_TwoVM.elf 带符号表，里面留着构建路径： 

/home/manuale97/Renesas_RH850/shangai-odyssey-auto-demo/bao-hypervisor/build/
    rh850-u2a-autosar-vm0+vm1/autosar-vm0+vm1/arch/rh850/aborts.o

PLATFORM=rh850-u2a-autosar-vm0+vm1、CONFIG=autosar-vm0+vm1—— 这两个在 odyssey 四个分支、archive 里的 tar 包、autoshow 三十多个分支里 一个都没有，只存在于原作者的机器上。

于是改从二进制里挖。ELF 有 _platform（0xfe10041c，380 字节）和 _config（0xfe100840）两个符号， .data.R 的 ROM 原像在 .data 段里，按结构体布局逐字段解出来即可。 关键是先定出步长：struct mem_region 内嵌 page_pool 是 40 字节， vm_config 76 字节，vm_dev_region 24 字节。

后续若要长期维护，把 CC-RH 工具链适配重新打到上游的 rh850 之上，比继续在旧私有分支上打补丁更可持续。

—复现步骤

# 0. 首次：装 E2 的 udev 规则，然后拔插 E2
cd <bao-benchmarks-portable> && ./install-udev-rule.sh

# 1. 编译
cd <repo>
export PATH=/usr/local/Renesas/CC-RH/V2.08.00/bin:$PATH
make PLATFORM=rh850-u2a-vm1+vm2 CONFIG=autosar-vm0+vm1

# 2. 烧录（guest + bao + 释放复位）
./flash/flash.sh

# 3. 看串口
picocom -b 500000 /dev/ttyACM0

之后只改 Bao 的话，make 完跑 ./flash/flash.sh bao 即可， guest 不用重烧。
