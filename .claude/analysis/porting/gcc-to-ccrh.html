—摘要

移植分六层：工具链、链接、汇编语法、内联汇编、编译器扩展、段放置。 除 __align 外，所有做法都能在 CC-RH User’s Manual 里找到正式依据。 核对过程中确认了两个真实缺陷和一处此前的误判。

—编译验证

用本机的 CC-RH V2.08.00 实际构建。初次编译失败， 18 个错误全部出自同一个根因；修复后两个平台都能干净链接。

阻塞项

匿名 union / struct 不能用 designated initializer

E0523134 · 6 个文件 18 处 
src/core/mem.c(168):E0523134:Anonymous unions and structures
                            cannot be initialized using designators

mem_flags_t（arch/rh850/inc/arch/mem.h）是含匿名 struct 的 union， 而六个 PTE_*_FLAGS 宏用 .e / .sr / .rmpid0 这些匿名成员做 designator。同样的模式还有 core/ipc.c 的 union ipc_msg_data 和 core/remio.c 的 union remio_cpu_msg_data。

注意成员访问是允许的——ipc_data.shmem_id 编译得过， CC-RH 只拒绝 designated 初始化。

修复取舍

位域成员在全树只出现在这六个宏里，没有任何其他访问点，所以有多种改法。 实测下来它们的代码体积差异很大：

01工具链替换

GCC 版原本按 CROSS_COMPILE 自动判别 gcc / clang 两套工具链。 CC-RH 版把整个分支逻辑删掉，写死为 Renesas 三件套。

编译命令同步换成 ccrh 语法，注意 -o 后不带空格：

$(cc) $(CFLAGS) -O$(OPTIMIZATIONS) -lang=c99 -c $< -o$@
      CFLAGS 里含 -Xcommon=rh850

代价：没有 objdump / readelf 就没有反汇编和 ELF 报告输出， 没有 strip 就不做裁剪。原来 GCC 版链接后会自动产出 bao.asm 和 bao.elf.txt，现在都没有了。

02链接方式：ld 脚本 → rlink subcommand

这是改动最大的一处。rlink 不接受 GNU ld 脚本，改成生成一个 subcommand 文件传入。

subcommand 文件里是 rlink 选项，段布局硬编码在 Makefile 中：

-input=<每个 .o 一行>
-library="<ccrh 安装目录>/lib/v850e3v5/rhs8n.lib"
-start=VECTAB,EINTTBL,.text,.const,.data,
       .ipi_cpumsg_handlers_id.data,.ipi_cpumsg_handlers.const,.bss/0,
       .data.R,.ipi_cpumsg_handlers_id.data.R,
       .ipi_cpumsg_handlers.const.R,.bss.R/fe100000
-rom=.data*=.data.*R,.ipi_cpumsg_handlers*=.ipi_cpumsg_handlers*.R,.bss=.bss.R

src/linker.ld 已经废弃

Makefile 的 $(ld_script_temp) 规则

Makefile 仍然会用 gcc -E 预处理 src/linker.ld， 输出到 linker_temp.ld.tmp.ld，但紧接着就用 rlink 选项列表 覆盖了 $(ld_script_temp) 本身。 那份预处理结果没有任何消费者，GNU ld 脚本不参与链接。 改段布局要改 Makefile，不是改 linker.ld。

手册对照：-form=absolute / -form=binary §7； -rom= 与 -start= 的组合用法在 §31 有示例 rlink a.obj b.obj -rom=.data=.data.R -start=.data/100,.data.R/8000， 与此处写法同构。

boot.S / exceptions.S 整体重写成 boot.asm / exceptions.asm，语法全变。

另一处影响更大：CC-RH 版不再预处理汇编。 boot.asm 开头的 ; TODO #include <arch/bao.h> 那几行是注释掉的，asm_defs.h / platform_defs.h 的常量在汇编里用不了，于是地址被直接写死： 

.public __data_addr
__data_addr:
    .db4 0xfe100000     ; 原本应来自 platform_defs.h

04内联汇编：__asm__ → #pragma inline_asm

CC-RH 不支持 GCC 的扩展内联汇编——没有 "r"(x) 约束，没有 clobber 列表。 改法是把每段汇编变成独立函数，函数体直接写指令，寄存器按 CC-RH ABI 手工对应。

ABI 约定

User’s Manual §9.1.1 / §9.1.2
角色寄存器说明
参数r6 – r9前 4 个字（16 字节）经寄存器传递，其余走栈
返回值r108 字节返回值用 r10 + r11（低 32 位在 r10）
Callee-saver20 – r31被调用方必须保存并恢复
Caller-save其余r1 由汇编器使用，r2 可能被 OS 保留，r3 是 SP

srs.h 里几十个系统寄存器访问器的 stsr n, r10, s / ldsr r6, n, s 写法与此完全一致。

用同样手法改写的还有：

  • inc/arch/fences.h — syncp / syncm / synci / synce
  • cache.c — cache 指令（目前全部注释掉）
  • asm_defs.c — 用 inline_asm 发射 .equ
  • spinlock.c — 见 发现的问题

代价：编译器看不见这些指令，不做寄存器分配、不做内联优化，也无法校验 clobber。 手册原文：“The compiler passes strings in #pragma inline_asm to the assembler as-is, without checking or modifying them.”

05编译器扩展的 shim

src/core/inc/bao.h 用 CC_IS_RHCC 宏隔了一层， 这个宏由 Makefile 全局 -DCC_IS_RHCC 定义： 

#ifdef CC_IS_RHCC
#define ATTRIBUTE_ALIGN(x) __align((x))     ← 见问题清单
#define FALLTHROUGH        // 空
#else
#define ATTRIBUTE_ALIGN(x) __attribute__((aligned((x))))
#define FALLTHROUGH        __attribute__((fallthrough))
#endif

src/core/inc/cpu.h 里也有一个 #ifdef CC_IS_RHCC， 但两个分支内容完全相同，是没写完的空壳。

06段放置：section 属性 → #pragma section

GCC 版用一个宏 CPU_MSG_HANDLER(ipc_handler, IPC_CPUMSG_ID) 就够了。 CC-RH 的 #pragma section 是作用于后续所有定义的区域开关， 不能包进宏里，所以宏被弃用，在每个调用点手工展开。

三处这么改：src/core/ipc.c:55、src/core/remio.c:135、src/core/mpu/mem.c:271。

段名是怎么算出来的

User’s Manual §4.2.6.1 规则 2
A string representing the relocation attribute is linked after the “user-defined name”.

预处理器把 section.ipi_cpumsg_handlers 切成 section、.、ipi_cpumsg_handlers 三个 token， .ipi_cpumsg_handlers 作为 user-defined name，编译器再追加重定位属性：

变量类型属性最终段名
__cpumsg_handler_* void (*const)(...) const .ipi_cpumsg_handlers.const
IPC_CPUMSG_ID volatile size_t = ~0 data .ipi_cpumsg_handlers_id.data

这两个名字正是 Makefile -start= 里排布的段 （加上 -rom= 生成的 .R 副本共四个）。段机制是生效的。

07asm_defs.h 的生成

这个头文件把 C 结构体的偏移和大小导出给汇编用。两套做法都是 “编译成汇编再从文本里抠”，但抠的东西不一样。

CC-RH 那条依赖 paste 把两次 grep 的结果按行号对齐， 只要 ccrh 的汇编输出顺序或格式变一下就会静默错位。比原来脆弱得多。

—发现的问题

问题

自旋锁实际是空实现

src/arch/rh850/inc/arch/spinlock.h · objects.mk

inc/arch/spinlock.h 里的 spin_lock / spin_unlock 是空函数体，里面还留着 RISC-V 的 amoadd.w.aqrl 注释： 

static inline void spin_lock(spinlock_t* lock)
{
    UNUSED_ARG(lock);
    /* ...全是注释 */
}

真正的 ldl.w / stc.w 实现在 spinlock.c，但 objects.mk 的 cpu-objs-y 里没有 spinlock.o，这个文件不参与编译。 头文件里的空实现赢了——ccrh 构建出来的锁是 no-op。多核上是实打实的 bug。

问题

备用锁实现破坏 callee-save 寄存器

src/arch/rh850/spinlock.c · Manual §9.1.1 / §4.2.6.2(2)

就算把 spinlock.o 加回编译，实现本身也有问题——它拿 r21 当临时寄存器：

#pragma inline_asm spin_lock
void spin_lock(spinlock_t* lock)
{
Lock:
    ldl.w [r6], r21      ; r21 是 callee-save，没有 save/restore
    cmp   r0, r21
    ...
§9.1.1 — Callee-Save registers: r20, r21, … r31。 这些寄存器必须由被调用方保存和恢复。
§4.2.6.2(2) — If you use a register to guarantee the entrance and exit of an inline function with embedded assembly, you must save and restore this register at the beginning and end of the function.

inline_asm 是在调用点内联展开的， 调用方正在用的 r21 会被直接冲掉。 改用 r10–r14（22 和 32 两种 -Xreg_mode 下都是可自由使用的工作寄存器）， 或者在函数首尾显式 push / pop r21。

问题

inline_asm 里的标签会重复定义

src/arch/rh850/spinlock.c · Manual §4.2.6.2(2)
When a label is written in an assembly-language function, labels having the same name are generated for the number of times the function is expanded inline.

spinlock.c 里的 Lock: / Lock_wait: / Lock_success: 是普通标签，而 spin_lock 不是 static，多处调用就会重复定义。手册给的解法是用汇编的 local label，或者保证只在一处展开。

问题

__align 不是 CC-RH 构造

src/core/inc/bao.h:29

手册全文 0 处提及 __align。CC-RH 的 #pragma align4 只管分支目标地址对齐（§4.2.6.11）， 不是数据对齐。

影响目前为零——ATTRIBUTE_ALIGN 在整棵树里 只在 bao.h 定义过，没有任何地方使用。 属于埋着的雷，哪天有人用就炸。

限制

VM_IMAGE 无法使用

src/core/inc/config.h:21

内嵌 guest 镜像的 VM_IMAGE 宏仍然是 GNU 内联汇编 __asm__(".incbin ...")，CC-RH 不认。 所以只能用 configs/null 这类空配置—— rh850-u2a-noguest 平台就是这么来的。

状态

非 CC-RH 特有的 WIP 项

  • 真实的 renesas_rlin3 UART 驱动被换成 dummy_uart，串口输出实际是空的

—更正记录

更正

#pragma section.xxx 的写法是对的

在拿到 User’s Manual 之前，仅凭应用指南里 #pragma section fw1（带空格）的示例， 曾判断源码里 #pragma section.ipi_cpumsg_handlers （带点、无空格）可能被当成未知 pragma 静默忽略，导致段为空。

这个判断是错的。§4.2.6.1 的 #pragma section user-defined-name 格式加上规则 2 的属性追加机制，正好解释了 Makefile -start= 里 .ipi_cpumsg_handlers.const 和 .ipi_cpumsg_handlers_id.data 这两个段名的由来。机制是生效的。

连带地，boot.asm 里手写 _ipi_cpumsg_handlers 等符号也不是“段机制失效后的绕行方案”， 而是 rlink 与 GNU ld 在提供段边界符号上的方式差异。

实际构建后的 bao.map 进一步证实了这一点：两个 handler 段各 0xc 字节、非空，见编译验证。
